# 企微作为 MCP 工具提交入口 + 按人隔离：分析结论

## 建议简述

- **入口**：通过企微提交/配置对应的 MCP 工具。
- **隔离**：工具按人员隔离（不同人看到/能用不同工具）。

本文档是对该建议的适用性分析，**不直接实现**，仅给出结论与推荐方向。

---

## 1. 概念拆分

「通过企微提交 MCP 工具」可以有两种理解：

| 含义 | 说明 | 风险与复杂度 |
|------|------|----------------|
| **A. 在企微里“登记/注册”工具** | 用户发消息如「添加 MCP 工具 xxx，serverId=yyy」，系统把该工具加入该用户可用列表 | 需解析自然语言或固定命令；若任意用户可自由添加，存在滥用与安全风险（恶意 MCP、配额等） |
| **B. 在企微里“使用”已分配好的工具** | 管理员事先按人配置好可用工具；用户在企微里和机器人对话，Agent 只调用该用户被允许的工具 | 无“提交”动作，仅按人过滤；与现有“按人隔离”完全一致 |

**按人隔离**：无论 A 还是 B，都适合引入「用户 ↔ 工具」的绑定关系（谁能用哪些工具），便于权限与审计。

---

## 2. 结论概览

- **按人隔离工具**：**建议做**。在架构上支持「用户 → 可用工具列表」，在 `listTools` / `executeTool` 时按当前用户过滤与鉴权，是合理且可复用的设计。
- **企微作为“提交/注册”工具的主入口**：**当前不建议做**。理由见下；若未来要做，建议做成「申请 + 审批」或「仅管理员在后台配置」，而不是任意用户发一条消息即可添加。

---

## 3. 为何“按人隔离”建议做

- 已有 **userId**：企微私聊/群聊在调用 Agent 时都会带上 `FromUserName` 或等价 userId，并传入 `runAgentLoop(goal, { userId })`，具备按人区分的基础。
- 需求合理：不同部门/角色可用工具不同；避免 A 用户触发仅允许 B 使用的 MCP；便于审计与合规。
- 实现方向清晰：
  - 存储：用户 ↔ 工具（或用户 ↔ MCP server）的允许关系，可用配置或 DB。
  - 接口：`listToolsForLLM(userId?)`、`executeTool(name, params, userId?)` 在存在 userId 时只列出/只允许该用户有权限的工具。
  - Agent：plan/act 里已带 `state.context.userId`，把 userId 一路传到工具层即可。

不一定要和「企微提交」绑定：先做「按人隔离」本身，入口可以是配置/API，企微只负责在对话时提供 userId。

---

## 4. 为何不优先做“企微提交 MCP 工具”

- **语义模糊**：在聊天里用自然语言「添加/配置 MCP 工具」难以稳定解析（工具名、serverId、参数等），容易误触发或需要大量提示词约束；若用固定命令（如「添加工具 mcp:xxx」），本质是一个小型 DSL，维护和提示成本不低。
- **安全与管控**：若任何白名单用户都能通过企微自行添加 MCP 工具，则可能指向不可信服务器、消耗配额、或误配置影响他人。更稳妥的方式是：**谁可以“添加/分配”工具由管理员控制**（配置文件、管理 API 或管理后台），而不是开放给所有企微用户。
- **与“按人隔离”解耦**：按人隔离是能力；谁有权限“为谁配置工具”是权限模型。先做前者，后者用现有配置或管理流程即可满足。

因此：**建议把“按人隔离”做成通用能力，“提交/注册”入口不首选企微**，而是配置或管理端。

---

## 5. 推荐路线（不直接实现，仅设计方向）

1. **先做按人隔离（设计 + 可选实现）**
   - 定义「用户可用工具」的存储（如：全局工具池 + 用户 allowlist，或用户级工具配置）。
   - `listToolsForLLM(userId?)`、`executeTool(name, params, userId?)` 支持按 userId 过滤与鉴权；无 userId 时保持现状（如全量或仅 builtin）。
   - Agent 在调用工具时传入当前 `state.context.userId`。

2. **“提交/配置”入口**
   - **现阶段**：不提供企微内“用户自助添加 MCP 工具”；MCP 工具由部署/配置统一注册，用户可见范围由「用户 ↔ 工具」配置决定。
   - **若未来要做“在企微里操作”**：更推荐「只读」类入口，例如：
     - 企微命令「我的工具」：展示当前用户被允许的工具列表（来自上述 allowlist），不提供添加/删除。
     - 可选：「申请工具 xxx」→ 生成工单/通知管理员，由管理员在配置或后台通过后生效，而不是用户发一条消息就直接写入。

3. **MCP 本身**
   - 当前 MCP 执行器仍是占位；按人隔离可与 MCP 接入并行：先有「用户 → 允许的工具名列表」，MCP 接入后，执行前再校验「该用户是否允许调用该 MCP 工具」。

---

## 6. 总结

| 点 | 建议 |
|----|------|
| 按人隔离工具 | ✅ 建议做，作为通用能力设计并实现 |
| 企微作为“提交 MCP 工具”的主入口 | ❌ 当前不建议；易产生解析与安全问题，更适合用配置/管理端 |
| 企微与“工具”的关系 | ✅ 企微继续作为**使用**工具的入口（对话触发 Agent 调工具）；可选提供「我的工具」等只读能力 |

以上为分析结论，后续若实现「按人隔离」或「企微侧只读/申请」能力，可据此在 `docs/tools/TOOLS-DESIGN.MD` 或代码中补充具体方案与接口。

---

## 7. 补充：管理端 UI + 按角色隔离（推荐模型）

### 管理端 UI 作为配置入口

- **提供管理工具的 UI 作为管理端**即可满足「谁可以添加/分配工具」的需求：管理员在后台配置，而不是在企微里自助提交。
- 这样既避免企微自然语言解析的复杂度，又保证只有管理员能维护工具与权限。

### “每人不同 token”为何会变成“都用我的工具”？

- 若不做隔离：所有用户（无论谁、什么身份）看到并可用的是**同一套全局工具**，相当于「大家都用这一套」（你提到的“都用我的工具”）。
- 若按**人**直接配置：每个用户单独配置一套可用工具，规模大时难以维护，且和实际权限模型（按岗位/角色）不一致。

### 推荐：按「角色」隔离 —— 工具是「这个角色下的工具」

- 项目已有**角色建模**（`roles` 表、`Role` 类型），适合把工具归属到角色上：
  - **角色 → 工具**：每个角色拥有一组允许使用的工具（如：运维角色可执行 MCP_告警、script_重启；开发角色可执行 get_current_time、mcp_query 等）。
  - **用户 → 角色**：每个用户通过 token/userId 识别身份，再绑定到若干角色（如从企微/SSO 来的 userId 对应到角色）。
- 这样：
  - 不同 token（不同人）解析出的 userId 不同 → 解析出的**角色**不同 → 看到的**工具集合**不同，不会「都用同一套」。
  - 工具归属在「角色」下，而不是「某一个人」或「全局唯一一套」，符合“应该是这个角色下的工具”的表述。

### 实现要点（设计层面）

| 点 | 说明 |
|----|------|
| **管理端 UI** | 管理「角色 ↔ 工具」：为每个角色勾选/配置可用工具列表；可选：管理「用户 ↔ 角色」的分配。 |
| **存储** | 角色已有 `roles` 表；可增加「角色 ↔ 工具」关系（如 `role_tools(role_id, tool_name)` 或把 `tool_names` 放入 `roles.config`）；若需持久化用户–角色，可增加 `user_roles(user_id, role_id)` 或由外部系统提供。 |
| **运行时** | 请求带 token/userId → 解析出当前用户 → 查其角色 → 取这些角色下的工具 → `listToolsForLLM(roleIds?)` / `executeTool(name, params, roleIds?)` 只列/只允许这些工具。 |

结论：**管理端 UI + 按角色隔离（角色下的工具）** 即可：既有清晰的管理入口，又不会出现「每人不同 token 却共用同一套工具」；每个人用的是**其角色下的工具**，与现有角色建模一致。
